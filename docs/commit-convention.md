# Git 提交约定

## 标题格式

```text
type(scope): 中文说明
```

`type` 使用下表中的小写英文，`scope` 是可省略的影响范围；冒号使用英文冒号，后接一个空格。说明使用中文，技术名称保留原文，以“新增、修复、统一、移除”等具体动作描述结果。标题尽量控制在 72 个字符内，不用句末句号，不写含糊的“更新代码”“修改”“完成今天工作”。

| 类型     | 使用场景                                                        |
| -------- | --------------------------------------------------------------- |
| feat     | 新增用户或系统可使用的功能                                      |
| fix      | 修复已有功能或数据处理错误                                      |
| refactor | 调整代码结构，保持对外行为不变                                  |
| perf     | 有依据的性能改进                                                |
| docs     | 文档、计划与协作约定                                            |
| test     | 测试与验证用例                                                  |
| style    | 仅代码格式变化，不改变行为；页面视觉功能调整按实际使用 feat/fix |
| build    | 依赖、构建与打包配置                                            |
| ci       | 持续集成工作流                                                  |
| chore    | 不属于以上类型的工程维护                                        |
| revert   | 撤销已有提交，正文写明原提交及原因                              |

范围优先使用业务域：`sales`、`products`、`promotion`、`aftersales`、`overview`；公共改动可使用 `web`、`api`、`sync`、`db`、`auth`。不必为每个文件创建范围；涉及多处但属于同一目标时可省略范围。

以下仅为格式示例，不表示功能已经实现：

```text
feat(products): 新增商品日明细分页查询
fix(sales): 修复跨月筛选的日期边界
perf(promotion): 优化推广趋势查询索引
docs: 明确飞书入仓过渡策略
```

## 正文与不兼容变更

简单改动可只有标题。涉及重要规则、数据迁移、较大调整或限制时，标题后空一行，正文说明问题与原因、最终行为、实际验证及未验证部分；数据库迁移另说明修复或回退方法。只写执行过的验证，不把模拟验证称为真实数据验收。

对已使用接口、配置或数据语义的不兼容变更，使用 `type(scope)!: 中文说明`，正文以 `BREAKING CHANGE:` 写明影响和迁移办法。`refactor` 不用于掩盖指标口径或用户行为变化。

## 提交粒度与推送

- 一次提交对应一个可解释的目标；不要混入无关页面改动或用户尚未完成的工作。
- 一个页面可分为契约、接口、页面、验证等多个完整步骤提交；不要求一个页面只有一个提交。中间提交必须如实标记状态，不把样本页面写成正式接入完成。
- 提交前检查差异并完成适用验证；仅文档变化进行格式与差异检查，不要求重复运行全部业务测试。
- 不提交凭据、业务数据、日志、依赖目录和构建产物，不在提交说明中暴露这些内容。
- Commit 保存本地版本，push 才会同步到 GitHub；汇报时区分“已本地提交”和“已推送”。不得未经明确授权改写已推送历史或强制推送。

当前通过项目约定执行，尚未配置提交信息自动校验；不能声称 Git 已自动拦截不合规标题。既有提交沿用原格式，不为增加 scope 改写历史。
