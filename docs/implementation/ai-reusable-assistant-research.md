# 公司共用 AI 问答：选型与落地调研

2026-11-17｜讨论稿。本文研究跨平台复用及运行方案；拼多多五页用例、首批问题和固定页面分析不纳入当前安排等产品范围，仍见[右侧 AI 问答计划](ai-assistance.md)。本轮只核查公开资料和已有观察，未安装试用、调用模型、接入数据库或测量性能。

## 1. 推荐方向

**先把拼多多的问答做成可复用的一套能力，等第二个业务接入并验证边界，再决定是否做成公司共用服务。** 运营在各自系统的右侧发问，助手用该系统的正式数据回答，能够追问、解释变化并指回依据。公司可以共用界面、会话、模型调用及验收方式；指标怎么算、用户能查什么，仍由各业务系统负责。

技术上建议从**现有 FastAPI 查数，再调用模型回答**开始。已能明确选定对象、日期和查询的题目，用一次模型调用就能验证效果。当实际追问需要模型决定补查商品、推广还是其他已发布数据时，**优先用 PydanticAI 核心库处理工具调用**。如果首批核心问题已经离不开补查，可以从首版就用，不必人为做两套。

**DeepSeek Harness（DSH）继续看，尤其要核实天猫现有服务能否复用。** 它更适合公司确实要运营一个可装配插件、可扩展工具和工作区的 AI 工作台。如果天猫团队能提供受控、可维护的助手服务，能通过相同的经营问答和权限验收，复用现有服务也是实际选项。“公司多个系统都能用”本身，并不要求先有通用插件运行时。

## 2. PydanticAI 和 DeepSeek Harness 的真正区别

DeepSeek 模型 API、PydanticAI 框架、DeepSeek Harness 是三个独立选项。**可以在 PydanticAI 里用 DeepSeek 模型，也可以单用 DeepSeek 模型 API。** 公司模型网关若存在，其授权和实际兼容性应单独核对。目前讨论的是 [PydanticAI 核心库](https://pydantic.dev/docs/ai/overview/)，其另有一套 [Pydantic AI Harness](https://pydantic.dev/docs/ai/harness/)，不在本轮推荐范围内。[DeepSeek 模型适配说明](https://pydantic.dev/docs/ai/models/deepseek/)

| 决策点               | PydanticAI 核心库                                                                                                                                                                                                                                                                                   | DeepSeek Harness                                                                                                                                                                                                                                                                                                                                          |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 放在什么位置         | 加进现有 Python 后端。FastAPI 持有业务身份、页面上下文、会话与查询；库负责模型和工具调用、结构化输出、运行控制。可参考[官方聊天示例](https://pydantic.dev/docs/ai/examples/conversational-agents/chat-app/)。                                                                                       | 以独立助手运行时为主要接入对象，有现成 Web 工作台和会话。可用 [Web 反代](https://deepseek-harness.github.io/deepseek-harness/en/guide/public-deployments)部署；[Python SDK](https://deepseek-harness.github.io/deepseek-harness/en/guide/python-sdk)管理本地 DSH 进程，不能把天猫 Web 地址直接当成 SDK 接口。                                             |
| 接一个新业务的做法   | 注册几个带参数说明的查询能力，运行时把已验证的身份和业务上下文交给工具。先用 Python 函数；独立业务需要跨服务调用时再接 HTTP 或 MCP。应用仍要做会话归属和结果核对。[依赖注入](https://pydantic.dev/docs/ai/core-concepts/dependencies/) · [工具](https://pydantic.dev/docs/ai/tools-toolsets/tools/) | 为业务配置专用助手、插件集合和允许的工具；工具可用插件，也可接[远端 MCP 服务](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/mcp/mcp-client/README.md)。仍要做业务访问控制、页面上下文传递、答案证据与工作区隔离。                                                                                                                  |
| “一切皆插件”值在哪里 | 能挂载查询、校验回答、换模型或工具；应用本身仍是宿主。只增加一种业务查询时，改动通常集中在本业务的适配代码。                                                                                                                                                                                        | 通过 [Cordis](https://deepseek-harness.github.io/deepseek-harness/en/develop/cordis-tutorial/) 和 profile，把模型适配、工具注册、会话记录、Agent 循环等拆成可替换组件。若公司需要让多个团队共用同一运行时、各自配装完整工作能力，这个灵活性是优势。只有新增几项只读查询时，用到的主要是工具注册。                                                         |
| 实际要自己做什么     | 站内侧栏与会话管理、权限、模型和额度配置、证据回链与审计。结构校验能检查字段形状，不能证明回答的金额或因果正确；需验业务结果。[输出校验](https://pydantic.dev/docs/ai/core-concepts/output/) · [可替换模型测试](https://pydantic.dev/docs/ai/guides/testing/)                                       | 接入公司身份、隔离会话和工具、限制工作区及文件访问、定义审计数据去向；如保留自有侧栏，还要核实嵌入或消息接口。多个插件一起上线时，要管插件依赖、版本和回退。[插件发布](https://deepseek-harness.github.io/deepseek-harness/en/develop/basic/publish.html) · [官方安全与成熟度说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/SAFETY.md) |
| 版本与维护           | 核心库稳定 V2，有公开[兼容政策](https://pydantic.dev/docs/ai/project/version-policy/)；小版本原则上不主动破坏公开 API，流式事件和 Beta 等有例外。固定依赖，升级前回放核心题，尤其是实际模型网关的连续工具调用。                                                                                     | 本轮已核对到 [v0.2.2-rc.3](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.2-rc.3)；官方仍定位开发预览。[rc.2](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.2.2-rc.2)已修复可选插件加载拖垮 Web 和重试重复提交等问题。若自托管，需连同插件、profile 和自有 UI 一起验证升级和回滚。                           |

在这个项目里，“公司可复用插件”可以先指**有明确输入、权限和出处的业务查询**。例如“查商品两期经营数据”由拼多多团队维护；以后其他系统可注册自己的查数能力，同时复用同一个对话和证据协议。这种拆法可用于 PydanticAI，也可在需要时接入 Harness，不必为了复用查询先统一运行时。

## 4. 公司共用什么，业务各自做好什么

| 能力       | 公司可共用                                                                                                                       | 业务团队保留                                                                                                                                                                                                |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 使用入口   | 统一侧栏体验、会话和引用样式。进入哪个系统，默认问哪个系统；确有需求再做明确切换。                                               | 当前页的店铺、商品和日期可作为提问默认值，界面让运营知道当前在问谁、问哪段时间。                                                                                                                            |
| 取数与分析 | 统一查询结果协议：对象、统计期间、单位及口径、完整截至日、缺项状态、出处。统一答案结构，让运营看得出哪些是事实、哪些是核查建议。 | 各业务负责同步、持久化和发布，维护已有指标、SOP、关联键及查询；返回当前获准的最少必要数据。AI 请求读取已发布结果，无须触发同步。                                                                            |
| 模型和运行 | 统一模型配置、费用与并发限额、超时、日志、提示词版本及回归方法；约定允许发给模型的数据范围、会话保留和清理。                     | 业务定义本系统可做的分析、SOP 生效范围、关键题目的正确答案。模型只能在本轮取得的证据上给结论；缺数据时说明缺口。                                                                                            |
| 身份与权限 | 接入经确认可用的公司身份；服务端按用户及业务系统识别会话，确定允许的工具。共享组件不能使两个系统默认互看历史。                   | 数据服务校验请求者的实际数据范围，页面筛选只帮助确定问题对象。拼多多目前匿名访问，浏览器会话最多用于隔开对话，不能替代跨系统访问授权。见[项目访问设计](deployment.md)和[数据可见范围](../requirements.md)。 |

例如运营问“这款最近 7 天为什么卖少了？”助手先明示商品、店铺、两段可比日期。业务查询按看板口径返回成交额、访客或转化等有依据的量；必要时补查能匹配的推广数据。回答可以说变化集中在哪几天、哪些指标同时下降，以及下一步查什么；若只有同期变化，不能据此判定推广导致下滑。若最新一天未齐，标明实际截至日。其他业务可以共用这种回答方式，不必共用拼多多的公式和表。

## 5. 为什么先不选其他路线

| 路线                                    | 什么时候值得选                                                                         | 眼下的取舍                                                                                                                                                                                                                                                                        |
| --------------------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 固定 SQL／已有领域查询 + 一次模型调用   | 已知查哪些指标，模型主要理解问法和解释结果。                                           | **首选起点。** 无须自己搭循环、长期记忆或工作流平台；已经有明确答案的固定报表继续由程序负责。                                                                                                                                                                                     |
| 让模型直接写 SQL 查库                   | 真有常用指标之外的临时统计需求，而且面向懂口径的分析人员。                             | 先不进运营首版。以后可另设探索模式，由服务端执行受限查询，专用只读身份只访问批准的分析视图，限制日期、行数和耗时；账号凭据不交给模型。结果标明探索口径。                                                                                                                          |
| Dify                                    | 公司明确需要运营或实施人员自行维护可视化工作流，并能承担平台运维。                     | [DeNA 实录](https://engineering.dena.com/blog/2024/10/dify-operation/)说明它能支撑内用服务，也显示自托管及自有 UI 仍有工程工作。当前主难点是经营指标与权限，画布无法替代业务查询。                                                                                                |
| FastGPT                                 | SOP/制度知识问答成为主场景，需要业务人员维护文档、版本和检索。                         | [平台披露的政务案例](https://fastgpt.cn/customers/government-public-services/government-provident-fund-intelligent-qa)可作知识问答参考。拼多多目前仅少量 SOP，预计最多几十份，先按场景和有效版本取适用段落；未完善的 SOP 不作为判定规则。实际经常找不到正确段落时再引入语义检索。 |
| LangGraph、跨系统通用插件市场、长期记忆 | 出现实质需求，例如可恢复的长流程、多个部门真正要独立发布插件、用户明确需要跨会话记忆。 | 先保留同一会话追问和经过评审的少量工具。业务增长首先表现为新增查询能力；每多一页或一份 SOP 不需要同时多一套流程。                                                                                                                                                                 |

四个项目的发布、兼容和修复记录，见[拼多多现有成熟度对比](ai-assistance.md#53-成熟度取证与选型建议2026-11-17只读调研)。

## 6. 怎么决定是否升级成公司服务

1. **先验证拼多多。** 选商品两期变化、接着追问推广，以及缺数或口径不一致的反例（见[首批候选题](ai-assistance.md#2-第一批建议支持的问题与预期回答)）。对照同一版本看板，把事实准确、解释有用和回答速度分别记录。清楚的问题先走已有查询；若反复需要模型选择后续查询，加入 PydanticAI 验证。
2. **并行核实天猫可复用什么。** 向维护方核实运行版本、是否有专用只读助手入口、身份怎样传到业务工具、会话隔离、日志保留、负责升级的人。先区分能复用的是模型网关、侧栏/工作台，还是完整的运行服务；一项成立不自动推出另外两项。满足关键条件后，再用相同题目比较 DSH 与 PydanticAI，尽量同模型、同数据、同口径。过关条件是数据对得上、追问不串对象、缺证据不猜、权限以内才可查询；再比较并发、失败重试、延迟、成本及升级回退。
3. **用一个真实的第二系统验证复用。** 先确认业务方、负责人、可用数据和用例。把它接到同一套问答与引用约定，检查新增工作是否主要是业务查询与口径，而不用复制聊天代码或改其余系统；同时验证身份、历史和工具隔离。不要求先做跨系统联合分析。只有复用收益、集中运维负责人及服务边界都明确，才建议独立部署公司问答服务；届时各业务仍可升级自己的查询。
4. **何时优先 Harness。** 公司现成 DSH 服务如果通过上面同题验收，且跨系统接入和后续维护成本更低，就值得复用。若公司进一步需要多团队插件装配、工作区或不同执行模式，可另做受控工作台试点。否则，以 FastAPI 加 PydanticAI 为跨业务问答的优先路线，按实际需求选择是否独立服务化。

## 7. 11/24 补充讨论 · 谁维护，哪些资料能回流

首版按拼多多团队自己交付右侧问答估算，建议采用 **FastAPI + PydanticAI**。若公司有团队承接现有 Harness，能提供拼多多专用的只读工具范围、用户及会话隔离，并通过同题对账，则优先复用该服务。天猫已验证 ChatBI 能查单品；当前维护人、外包支持范围、接入条件仍需红薯确认。以下比较的是各团队要承担的工作，尚无本项目的工时或费用实测。[天猫实测](../source-evidence.md#tmall-ai-implementation-20261123)

| 选择                       | 拼多多要维护什么                                                                                                     | 谁负责服务与升级                                                                                                               | 多系统复用的收益与代价                                                                               |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| 接公司现有 Harness         | 右侧入口、页面商品与期间、限权业务查询、SOP 和答案对账。可嵌入已有聊天界面。                                         | 建议由确认接手的公司平台团队或有明确服务范围的外包维护宿主、模型接入、插件组合、故障恢复与兼容性。拼多多负责本业务数据和接口。 | 多系统可以共享工作台和运行费用管理。要验证一次更新对各业务的影响，以及共享服务故障时谁恢复。         |

例如给现有经营查询新增一道“按款查推广”的题，Harness 可挂业务 MCP，PydanticAI 可注册 Python 函数；两条路都要验证同款、同期间和同指标。插件减少重复开发。自托管仍需运维外部入口并检查加载的插件，PydanticAI 升级仍需验证流式回答和工具调用。[Harness 部署](https://deepseek-harness.github.io/deepseek-harness/en/guide/public-deployments) · [Harness 官方状态说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/SAFETY.md) · [PydanticAI 工具](https://pydantic.dev/docs/ai/tools-toolsets/tools/) · [PydanticAI 兼容政策](https://pydantic.dev/docs/ai/project/version-policy/)

**资料回流可以先用现有飞书 SOP。** 建议运营把有价值的案例或纠错提为候选，由业务负责人核对证据、适用系统、有效日期和可见范围，再更新对应 SOP 或指标口径并保留版本。涉及判断规则时，工程同步相应查询或规则及验证题。下一次问答读取生效版本，经营数字仍按当次对象、权限、期间重新查。两种运行方案都能采用这一流程；几十份资料先按场景索引。Harness 官方另有可选的第三方记忆服务接法，示例默认关闭，外部存储、数据迁移和服务托管各需有人负责。[Harness 记忆服务说明](https://deepseek-harness.github.io/deepseek-harness/en/guide/mcp-memory)
