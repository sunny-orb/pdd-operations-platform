# 项目数据库迁移到 pdd_dashboard

## 授权与运行约束

2026-11-10用户要求将pdd_operations项目表完整迁入pdd_dashboard，确认无误后删除旧库；任何改动均需报告，并要求不影响线上运行、不占多余空间。迁移不改变业务对象、字段、关系、指标、删除策略或来源；沿用[数据库设计](../database-design.md)与现行字段字典。上线位置仍为同一PostgreSQL实例，不新增缓存或数据库服务。

用户已接受临时双份空间和短暂切换窗口。最新明确接受售后接入现状，指示清空旧库，不再以该来源同步失败阻塞本次清理；旧数据库本身由管理员后续删除。本轮清理仅限旧库32张项目领域表的数据，保留空表结构、Alembic版本记录、公司monitor/repack及扩展对象；新库及线上服务保持。

完整迁移必须保留表数据、主外键、唯一及检查约束、索引、序列、函数、视图、所有权/权限及Alembic版本。不能只搬业务事实而遗漏版本、输入关系、规则和运行记录。公司monitor及扩展属于公共运维对象，目标已有对象不得覆盖；删除源库前需确认这些库级对象和监控连接的处置。

## 执行设计与门槛

1. 只读盘点源/目标对象、使用连接、权限及发布依赖；证据见本次核查（2026-11-10本地验收记录）。目标存在未知对象或同名业务对象时停止覆盖。
2. 短暂切换窗口及临时空间已获准。当前单API部署不具备已验证的无中断数据库切换能力；源库占用不等于恢复后占用或所需峰值。数据库主机监控显示根分区可用26,819MiB、/data可用175,576MiB，data_directory为/pg/data；其符号链接/挂载映射尚未核实，不将某个分区余量直接认定为数据卷余量。
3. 适配发布检查中的固定库名及必要配置，并在真实PG隔离库验证；不改已执行Alembic revision、不借迁库增删字段。现有镜像的维护入口仍固定旧库，须交付兼容的维护工具，不能仅修改连接串后留下发布故障。
4. 确认写入方、取得项目同步互斥并等运行任务完成后暂停Worker。使用同一一致快照备份与核对数据；优先流式传输，避免在应用服务器重复落盘。不逐表搬完即删，源库在验收前完整保留。
5. 恢复到已核空业务范围的目标，检查对象清单、逐表行数/内容摘要、约束索引、权限、版本和关键API输出。恢复失败不触碰源数据，只按明确清单处理本批次目标对象。
6. 在批准的切换窗口调整API、Worker及维护/备份连接，验证全部页面、关键接口、同步及新写入落点。只读API可在复制期间继续读源库；单实例切换可能短暂不可用，不能称零中断。
7. 观察覆盖实际同步时点后核对无旧库依赖，并验证备份恢复。旧库业务数据清理前报告验收及空间清单；删库由管理员后续处理。用户后续明确接受售后同步未通过项后，可在迁移数据、备份及线上连接验证通过的条件下执行本轮退役清理。目标开始新写入后的回退需保全新增数据，不直接切回旧快照。
8. 完成后清理本批次无用临时材料，不保留第二套运行库；必要恢复备份按明确保留规则处理，不以省空间为由提前删除。

应用表存在公司dbrole_readonly/dbrole_offline/dbrole_readwrite/dbrole_admin的显式授权。迁移必须保留并逐项对比ACL；既有备份工具使用--no-acl/--no-owner，仅适用于其隔离演练，不能原样用于本次完整权限迁移。已有恢复工具和源库旧名断言也须适配，但不改历史备份清单或篡改历史恢复记录。

## 变更报告与验收

逐阶段报告文件/配置/数据库对象、原值与新值（不含秘密）、原因、验证和回退。代码改动执行项目规定检查和真实PG验证；交互验收使用浏览器。只读预检不代表迁移完成。执行进度统一见[TODO](../../TODO.md)。

## 切换与回退基线

独立审查确认旧镜像维护入口拒绝新库名。先在旧库发布兼容新旧库的维护版本，验证后使用同一兼容清单执行连接切换，让当前及上一发布快照均具备新库维护能力。旧业务镜像不作为切库后的直接回退目标。连接配置回退与数据回退分开：目标首次写入前可恢复旧连接；目标写入后必须保全增量，不能直接切回旧快照。

## 旧库数据清理实施

本次为退役库数据清理，不改变业务对象、关系、字段或现行Alembic链。删除对象为public中既有32张领域表全部行；唯一保留的项目表行是alembic_version_v2的结构版本记录，避免空表结构与迁移元数据不一致。

1. 核对已验证密文的SHA-256，确认33表全行摘要/结构权限验收记录；再次读取API/Worker真实连接及服务健康，拒绝仍指向旧库。
2. 在旧库单事务取得项目32表及版本表的排他锁，5秒锁超时失败即停止；确认除公司监控外无业务连接。核对公司受保护对象、完整元数据及固定TRUNCATE保护触发器清单，拒绝未知表/触发器。
3. 在持锁事务内对33表重新计算完整行数和内容摘要，必须仍等于已迁移并备份的源快照。确认新库仍保留全部原有版本记录并正常读写；任何差异回滚、不清理。
4. 对固定32表显式执行一次TRUNCATE CONTINUE IDENTITY RESTRICT，不使用CASCADE、不清空public schema、不禁用约束。在同一持锁事务内只临时DISABLE旧库30个已核实的BEFORE TRUNCATE保护触发器，执行后全部ENABLE回原状态；不禁用其他触发器或更改函数。事务内逐表检查0行、版本记录保持、完整元数据（含触发器状态）及公司保护对象不变后提交；失败整事务回滚。
5. 提交后重新核对旧表空、实际库大小、新库服务及公司目录占用；记录释放空间。无需VACUUM FULL，不重启API/Worker，不删除其他备份/归档。

提交前任何检查失败均回滚；提交后恢复需从已验证密文恢复到隔离环境并按实际新增数据对账，不允许直接把线上切回旧快照。密文继续保留，后续删库由管理员处理。
