## 目标、依据与边界

### 2026-11-18 当前容量核查与治理取舍

本轮用户要求保留正常取数、全部历史报告与展示，不增加持久副本或生产负担；授权先本地验证、通过后发布。线上仅以5秒语句超时读取本库目录统计，未扫描事实、执行删除或维护。当前`pdd_dashboard`为17.058GiB，其中五张旧表示事实共16.338GiB：售后销售6.525、退货4.109、商品地区3.155、商品日2.173、商品推广0.376GiB；均包含索引，不能当成可删除空间。售后两表同时包含JST与RPA，不把整表都算旧JST。统计死行接近零，不以普通VACUUM能明显缩库为前提。

三类非售后新版本内容复用已启用，未变化块不因producer改变复制；存量旧表示不会自动转换。旧JST采集已停，历史输入仍被报告引用。RPA相同完整输入复用已发布版本、producer不参与接收摘要；但原始`updated_at`变化仍能令接收摘要变化，而规范经营行不变，当前会整期写新事实。这个合成反例已确认，生产发生频率未测，不能据此归因17GiB。

本机最近两份JST版本的有序小样本显示源定位键变化，而排除定位键后的经营载荷有重复；现有共享桶把源键纳入身份，不能直接套用合成去重率。无损存量优化应先验证完整业务值、逐版身份和重复行次数，再设计共享载荷与必要身份映射；必须保留报告/版本/比较绑定及旧事实ID，不按款号合并行、不改published为draft或禁触发器。先在隔离PG实测目标表、索引、临时空间、事务与恢复成本，再确定逐批维护方案；未证明净收益前不转换。

本轮先降低同步中间对象及查询开销，不新增存储格式、不开生产删除、不扩RPA共享命名空间。容量存量项继续开放，不声称已缩至原7–8GiB。即使删旧表示，普通VACUUM主要使页可复用；`VACUUM FULL`会重写表、需要额外空间和排他锁，与本轮安全负载边界不符，见[PostgreSQL17空间回收说明](https://www.postgresql.org/docs/17/routine-vacuuming.html#VACUUM-FOR-SPACE-RECOVERY)。

减少同一经营数据在多个发布版本中的整份复制，保留五页已有查询范围、全部历史售后报告修订、比较绑定、来源证据和失败恢复能力。先处理可恢复的旧副本，再减少新增重复；不以删除经营日期、缩短同比范围或隐藏旧报告换空间。

## 一、明确留什么、清什么

“清理”指从在线PG移除已有可验证离线备份的旧事实副本；经营历史并不永久销毁。现有线上可访问的报告和日期范围全部保持。下列数量规则、24小时缓冲用于本地第一阶段；生产未启用。

| 对象                                           | 在线保留规则                                                                | 允许清理的边界                                                                                                  |
| ---------------------------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 当前经营事实                                   | 每个逻辑数据集当前版全部事实，包含它实际覆盖的历史日期和同比输入            | 不按日期删、不删除当前版内“看起来相同”的行                                                                      |
| 回退版本                                       | 当前版之外，最近一次真实成功发布的不同版本；递归保留其输入                  | 至少当前＋上一成功版，不能按created_at简单取两行；A→B→A须保留B                                                  |
| 历史售后报告                                   | 所有published报告修订、原report_id、规则和输入、上期/同期比较报告及递归依赖 | 第一阶段全部在线，不仅保留每个月的最新修订；相应销售/退货事实不清                                               |
| 天气历史                                       | 全部现有发布ID及正文、修订，保持已有历史入口                                | 体积小，第一阶段不清                                                                                            |
| 商品地区、商品日、商品推广的旧事实             | 保护集合中的版本全部在线；退出当前入口后至少观察24小时                      | 仅完整版本退出保护、无未知引用、可恢复且逐条批准时，列为第一批候选                                              |
| 资料、店铺、链接、目标、规则、标准、评分及子项 | 第一阶段原样保留，尤其profile_record_id、standard_id等显式FK目标            | 暂不为约几十MiB收益扩大清理面；以后另审查具体表与子项                                                           |
| 版本、输入边、任务、覆盖与来源状态             | 保留小型元数据；离线位置和恢复状态明确可见                                  | 不删dataset_versions、version_inputs、task_runs、current_datasets、coverage_records或source_checkpoints来省空间 |
| draft/rejected/失败/孤立/未知批次              | 先保留证据、辨明写入者和未完成事务                                          | 本轮策略不自动清；不能只按文件名、旧日期、state不是published来删                                                |
| 本机离线数据包与恢复密钥                       | 已删除线上副本的包保留；清楚登记位置、摘要、依赖和密钥位置                  | GitHub main不含经营数据，不能据此删离线包；唯一恢复副本不自动过期                                               |
| 索引、约束与公司对象                           | PK/UQ/FK、封版保护和公司预装对象保持                                        | 不因idx_scan=0删索引，不全局prune、不清schema、不禁触发器硬删                                                   |

第一批明确只设计product_region_records、product_daily_facts、product_promotion_records三个事实表的旧完整版本离线，不包含上表其余领域表。这对应11月9日约2.67GiB的历史估计，比原2.75GiB总候选更保守；新增24小时缓冲、实际依赖或数据变化可能进一步减少可清范围。不得拿7.62减2.67当预计磁盘读数。

## 二、怎样算保护集合

保护由实际引用决定，数量/天数只作最低保留，不能覆盖引用保护。

1. 根节点包括全部current_datasets、各数据集上一成功的不同版、全部可访问售后报告及天气发布、仍在执行任务的输入/结果、批准保留的审计/回退版本。没有可验证的上一版序列时保守多留；不能把较晚创建但从未成功启用的版本当上一版。24小时从最近一次真实退出当前入口开始计算，采用可靠发布序列中后继切换完成的时间作保守起点，不能用sealed_at；A→B→A→C中的A须从最后退出重新计时。无法重建退出事件时继续保留，并在维护能力上线后记录可信切换事件。
2. 对version_inputs做传递闭包，同时追踪aftersales_reports的previous_report_id/yoy_report_id，评分到standard_id、资料关系到profile_record_id及其父版本。重新盘点所有项目FK与代码中的非FK引用，未知表、字段或新消费者立即拒绝生成可执行清单。
3. 识别当前历史推广补齐等非主来源，保护其真实入口与消费者；不能以“没有定时同步”判断未使用。若历史回放/导出工具可直接查旧ID，也须列入使用者清单，否则该版不进入清理。
4. 保留现有数据库元数据和共享维度。第一阶段其他表不删，因此仍有历史派生产物指向候选的可能；必须明确其输入已离线，所有重放/再发布入口走统一在线可用性检查，不能只检查父版本state=published。
5. 候选同时满足：已published、属于三个批准表、最近一次退出当前入口超过24小时、退出全部在线根及依赖、没有运行任务使用、内容不可变且清单完整、有已验证的可恢复包。缺一即保留。
6. 清单逐版本列出数据集、版本ID、表名、精确行数/摘要、实际日期分布、依赖与排除理由、包ID、恢复证据、估计空间。每次apply只允许批准清单与现场候选的交集；发现变化停止重算，不自动扩大范围。

第一阶段不删除任何旧报告，也不把它们的输入改绑到最新事实。比如十月月报有多次修订，既有report_id继续读取原版本、原分类规则、原上期与同期结果；打开旧链接应得到与清理前相同的结果。

## 三、使“已发布但离线”成为明确状态

现有schema不支持安全移除封版事实，因此第一阶段也需要先做本地设计、迁移和代码验证。不能将旧库退役时的整库TRUNCATE方法用于仍运行的新库。

### 新增运维对象的设计边界

| 拟新增对象                                      | 对象与关系                                                             | 必需字段/约束                                                                                                                          |
| ----------------------------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| dataset_storage                                 | 一个数据集版本的在线存储状态，version_id为PK/FK到dataset_versions，1:1 | version_id、state、archive_id、changed_at；state仅online/offline，offline必须有归档引用；业务published状态、指纹、时间和原输入关系不改 |
| retention_archives                              | 一份经过验证的加密版本归档，1:N版本                                    | id、目标库标识、schema head、格式修订、密文摘要、清单摘要、文件位置、验证/恢复演练时刻；不存密码/密钥；有已离线版本引用时禁止删除登记  |
| retention_operations及retention_operation_items | 一次受控清理或恢复的审计，操作1:N明细                                  | 操作ID、清单摘要、policy修订、代码修订、状态及真实时间；明细固定操作/版本/表、行数与内容摘要、执行结果，不把版本引用藏在任意JSON中     |

执行实现前，按数据库设计流程补齐字段字典、PK/FK、CHECK、UQ、索引及删除规则；ID维持项目字符串约定，时间使用TIMESTAMPTZ，数量非负，密文/清单摘要验证格式。清单JSON只容纳文件目录等运维元信息，不替代业务关系；操作明细独立子表，(operation_id,version_id,table_name)唯一，FK删除RESTRICT。这些是运维证据，不改变经营事实范式。

新增Alembic revision，先扩展元数据并将既有版本登记online，再交付所有读写入口的状态检查，最后才能启用维护。新版本必须在发布事务中登记online；迁移过渡的兼容行为仅限清理开关关闭期间，启用后缺少登记即拒绝维护/复用，不默认在线。

字段与约束已细化到[运维字段字典](../database-schema/database-retention.md)。追加dataset_publications原子记录真实指针切换，原有task_runs不足以可靠还原每个来源的历史退出时刻，因此不猜测补造旧事件。当前实现保守保护全部非白名单版本及其输入闭包，可能多留一部分不再被当前页面读取的旧数据；以安全为先，不保证此前估算的候选容量仍可释放。

现行CLI和Python维护入口限定127.0.0.1:55432、pdd_admin和随机测试库；18额外允许已授权的精确本机pdd_operations业务库，连接与数据库触发器共同核对实际身份。配置production_apply_enabled=false不可用于解锁生产。真实生产维护能力、批准双故障域副本和首轮完整生产业务基线仍是后续独立门槛。

### 受控删除与恢复

- 普通应用对sealed事实的增改删继续被拒绝。新增窄范围维护通道只处理批准表、固定版本、已登记操作和已验证包；同一事务锁住版本/存储状态，复核保护集合与指纹，再删事实并改为offline。只允许online→offline，恢复只允许offline→online。
- 不采用session_replication_role、不DISABLE TRIGGER、不删约束、不改published回draft、不清空整表。受控通道必须由数据库约束和触发器校验操作范围，不能单凭调用方传入一个布尔开关放行。songbing仍是现有owner，此处是误操作防护，不宣称能防止owner主动改DDL。
- 每个版本原子处理，默认一次维护仅执行一个版本，然后验收再处理下一个。跨表对象以后纳入时需同组原子处理；不能删除一半却登记offline。预演达不到短事务预算就停止，另行设计可恢复分批协议，不能自动放宽限制。
- 恢复到原ID、原业务值、原版本，缺失行插入、相同已有行核对、不同内容拒绝覆盖；恢复前后行数/内容摘要、FK/唯一约束和业务结果一致才改online。恢复不移动current，不触发上游或通知，不覆盖恢复期间新增的其他版本。包内DDL只用于新建的隔离库，不向生产直接执行：若包的schema head/格式与生产不一致，先按原head隔离恢复，再经已批准的迁移/格式适配并验证原语义及新表示摘要；无已验证适配路径就拒绝在线恢复。之后每次schema升级都必须验证仍保留的离线格式恢复，不能只测试online事实；备份保留相应恢复工具和可获取的依赖版本。
- 指纹复用命中offline时明确返回恢复需求、保留当前成功版，不把无事实的历史版本推进current。不能为了省事造同指纹新版本或重拉今天的上游冒充当时数据。必要回退输入的状态也要检查。A→B→C→A若A已经离线，本次同步会暂缓发布并保留C；备份介质离线时不能承诺即时恢复。必须在状态里明确“旧数据可用、待技术恢复历史输入”，不能伪装成上游故障或宣称同步无影响；由维护人员恢复，不让运营人员修数据库。
- 离线版本不属于现有公开查询根。若仍被某API显式请求，返回明确不可用/需恢复，不能空集200或补0；这类入口本应在保护盘点中排除，出现即停止清理并补保护。

## 四、备份、并发与失败恢复

### 先证明能恢复，再删在线副本

候选导出必须包含PG事实的原ID和全部列、相容schema定义、版本与依赖清单、规则/解释/生产者证据及必要原始输入的位置和摘要。之前的原始文件tar包不能直接充当数据库行备份；若已有文件离线，要解析既有回执并核实那份包仍可读。唯一历史事实即使不在当前页面范围内，也必须随版本留在离线包中。

使用固定只读一致快照导出，服务端流式传出，不再堆积一份服务器明文全库。包加密保存于本机Git忽略的var/production-db-archives/<包ID>/，恢复密钥与包分开保管。正式apply前须达到：

1. 候选包完整接收、解密成功，清单、每表完整行数与全量规范内容SHA-256通过；Decimal、NULL、JSONB、时区、原ID不能有损转换。
2. 在127.0.0.1:55432本机随机隔离PG库中，恢复schema与所需元数据/维度依赖，原样恢复候选数据；约束索引有效。不得向生产测试库或其他人的库恢复。
3. 所有现有历史report_id的接口结果作为前后对账对象，覆盖报告清单、总览、分类、单款、原因及可用筛选路径；原比较绑定不变，金额/数量/NULL/缺失状态严格相同。小数不靠容差掩盖差异；运行时间、request_id等非业务字段独立比较。
4. 当前及上一版的五页API结果、趋势/同比/筛选/评分依赖，和版本/内容摘要一致。文件备份、数据库快照与当前生产发布版本有明确对应，不混用不同时间点的包。
5. 有两份独立故障域的可解密副本（如本机＋公司批准的备份介质），并有密钥独立保管记录。第二介质未配置时，可完成本地实现和清单，但生产删除保持关闭；不得擅自上传到外部存储。两份包只是本机两个文件夹不算独立副本。

一次完整项目恢复演练作为首次维护门槛；之后每个新候选包也须做对应版本恢复验证。恢复所需的旧依赖包不能先过期。长期备份仅允许淘汰已被另一份完整、验证可恢复副本替代的重复代次，唯一归档不自动到期。

### 不让清理碰上同步发布

导出和隔离验证期间可正常服务，删除前取项目维护锁并按统一顺序取得现有全局/领域发布锁：project-source-sync、m1-product-board、m5-source-report、nmc-weather-publication和实际m3-*范围；对独立手工导入、评分、恢复、迁移入口逐项核对，不假定只停定时器就没有写入。若引入新锁，必须让全部写入口遵守，旧镜像不得执行清理。

拿不到锁或发现运行任务就退出，不杀任务、不重启共享服务。锁内用新快照重读current、上一版、全部报告与FK/其他根、候选摘要及备份登记；引用变了就停止。本地默认预算为锁等待1秒、单版本维护事务总计30秒；读取策略中的更严格时限，SET LOCAL lock_timeout、statement_timeout与PostgreSQL 17 transaction_timeout，不改全局。事务总时限与statement_timeout_ms同值，避免多条短SQL累计无限持锁。预算需隔离压测验证；超时整版回滚，不能自动提高超时或减少检查。计划过期、版本被新报告引用、恢复包不可用、未知对象出现均停止。

API/Web保持运行，读事务固定一致快照；当前/回退/历史报告数据根本不在删除集合中。写入锁只短时延后同步，不承诺零延迟。现有SYNC_ALREADY_RUNNING/409及already_running在维护占锁场景应归为可重试的维护延后，保留到期槽与接收水位，释放后有限重试，不能误记上游接收失败或永久消耗本轮调度槽；该区分须随维护能力一起实现并测试。全量导出与内容核验不放在删除持锁阶段，锁内核对已封版内容与核验清单的绑定和必要变化标记；任何无法证明未变的情况退回重新核验。MVCC使删除前开始的读事务可见原行，但不能用它替代引用保护或忽略长事务造成的回收延迟。

失败时：提交前回滚该版、保留current；多版维护已成功的版继续登记offline，停止余下操作，不声称全批回滚。事后发现问题从验证包恢复指定版，不恢复整库覆盖新数据。恢复未通过就保持不可用标记，绝不补0或改挂最新输入。

## 五、长期减少新增副本

只做上面的存量清理仍会增长。优先在占用最大的售后销售、退货事实域实现“版本保持独立，未变化内容复用”，然后再扩至另外三个大表。当前所有历史报告保持在线，这是新增数据层实现要满足的要求。

推荐按确定性内容块复用：每个数据集/表/字段语义命名空间内，先按业务日期/统计期间分组，再以稳定source_row_key的哈希前缀作桶；桶内按键排序并包含全部原值、类型、NULL、规范关联和单位，产生不可变内容摘要。一个版本关联完整块清单；内容相同的块只存一次，不同内容写新块。使用稳定键分桶，避免按页码切块时插入一行导致后续全变。桶数/块大小根据真实数据及查询测试选择，写入格式修订后固定，不能运行时任意调整。

- 把接收/producer追溯与物理内容身份分开：producer仍保留在版本上，规范行内容没变才复用块。解释/结构/单位变化必须经过兼容性校验，不把不同语义的“相同数字”混为一块。
- 原业务键、版本ID、report_id、比较链与查询输出不变；不合并不同来源或不同粒度。来源删除/修订只改变新版本的成员清单，旧版本仍引用旧块；不靠来源当天没读到某行推断删除。
- 不做无限“上一版＋差异链”，每一版直接持有完整块清单，恢复和查询无需追溯无限长链。规则和来源证据仍能精确重现。
- 版本→块为N:M关系，块→类型明确的事实行1:N；实际字段仍用各域关系表及NUMERIC，不把所有业务事实塞进通用JSON。已有行ID引用、唯一业务键和跨块重复键约束须在专用字段设计中逐一迁移和验证。
- 垃圾回收按所有在线版本/报告、进行中的发布及恢复引用求可达集合，不依赖容易失真的手工计数；被任何受保护版本引用的块不可删。未引用块也必须满足备份/缓冲/批准条件。
- 本机统一适配五类大事实，默认关闭并限定随机测试库；查询层兼容旧行存储和新块存储。生产采用逐域启用并另行验收，逐版全量对账、并发和性能验收后才讨论既有历史转换。旧表示在验证通过前保留，但明确峰值空间预算；不能把全库再复制一份且长期不清。

此阶段先做本机合成数据试验；启用生产前还须代表性业务规模验证，测量去重率、索引占用、整版/筛选查询耗时、写入与恢复成本，再确定表/索引/桶参数。若没有明确收益或性能退化，不迁生产。复用改善重复开销，真实新增经营历史仍会增长；不承诺数据库永远固定大小。

不推荐直接删除旧报告修订或改为最新事实动态重算，这会改变旧链接和历史数值；不以单纯定期VACUUM FULL作为长期方案。

## 七、容量、备份周期与停止条件

建议每次同步成功记录版本数、事实新增/复用量与耗时；每日一次生成只读容量/候选报告，记录数据表、索引、归档、备份分别占用，不按每页刷新扫描大表。建议每日一次加密项目备份，并验证恢复链；具体时点依据同步/负载测量安排。本方案不创建定时任务，不设置自动删除。

数据库容量上限及告警值需用“受保护实际体积＋最大来源批次＋索引/WAL/维护余量”实测，再由可用配额决定；当前12GiB只限制文件归档，不能拿来当PG上限。本机32GiB例外也不修改线上预算。空间不足、备份介质不可用、恢复校验失败或API结果变化时停止清理/迁移，保留现有成功数据，告知影响和下一次可恢复条件。

DELETE通常先形成可复用空间，不立即归还OS；第一目标是降低重复写入并复用空闲页。若确需收缩文件，单独评估本项目表的维护窗口、额外磁盘和锁，再决定是否执行。VACUUM FULL会锁表并需要临时空间，本轮不计划执行，也不调整共享数据库autovacuum。参考[PostgreSQL空间回收](https://www.postgresql.org/docs/17/routine-vacuuming.html)及[事务隔离](https://www.postgresql.org/docs/17/transaction-iso.html)。

本方案保守默认：全历史报告在线；第一阶段只清三个大表的非保护完整版本；当前＋上一版＋24小时缓冲；验证过的独立双副本才允许生产删；自动删除关闭。需要业务选择的“历史报告保留多久、是否永久销毁旧经营数据”不在本阶段动作中，因此不阻塞只读规划和本机验证；若以后要改变，再单独确认。

## 本地工具与恢复包边界

入口为scripts/database-maintenance.py，无动作参数时只执行plan；export要求显式冻结清单、单候选、项目var/production-db-archives子目录及独立存放的32字节600权限密钥文件。verify验证全包AEAD/文件集合/摘要；drill新建并销毁本机随机PG库，成功生成绑定密钥的回执；18的apply/restore另允许已授权本机业务库管理员，生产继续拒绝。部分包保留为排障证据，但没有完整manifest和成功演练回执不能维护。旧schema/格式需要已验证适配器，本轮没有通用降级或自动适配旁路。

每包包含一个候选的精确COPY原行，以及恢复外键所需的元数据、小表、运维审计和必要原始输入证据。隔离演练库只用于该候选与约束校验，不代表恢复了其他未打包的大事实或完整看板；不得把它交给业务使用。完整项目备份仍采用全项目pg_dump，首次生产维护还需完整项目恢复验收。当前本机回执明确production_approved=false；本机加密包和隔离演练不是两份独立故障域副本。

维护不安装定时器、不自动扩展候选。apply持锁后重算保护/当前/退出/结构关系，正常封版保护保证已核验事实不被应用改写；删除行数和离线标记在同一事务提交，数据库延迟约束拒绝半完成操作。restore只恢复指定版本原行，重复恢复先核对既有内容，冲突拒绝覆盖。回执、清单、包均不得提交Git。
