# 跨看板筛选统一方案

本文区分已授权的筛选修复与后续统一建议。2026-11-03用户确认将商品总览、商品明细和商品推广的等级分组统一；本轮只实施下面的等级任务。其他跨页联动、销售、售后和中心不在本轮范围。已确认口径以data-contract为准。

## 等级统一实施（2026-11-03确认）

沿用现有React/TypeScript与FastAPI，在原开发目录和5173入口实施，无表结构或上游同步变更。共用分组、匹配和成员说明，继续使用现有下拉控件。

1. 在`product_board/filter_projection.py`提供`level_group(info)`、`matches_level(info, wanted)`；M1/M2查询和目录共用。原`level`、成员和风险资格不覆盖，旧混合等级条件保持精确匹配。两域查询版本纳入共享文件。先用真实PG验证互斥分组、跨店身份、重复资料、无等级、新品混合和旧链接，再接实现。
2. 商品轻量目录保留原`level`，增加`level_group`和`level_details`；前端`catalog.ts`按分组生成选项、按同一规则匹配。`shared/products/levels.ts`复用成员说明，商品候选和明细显示具体成员；推广迁入同一说明函数。先验证多等级筛选、基础等级排除混合、旧精确条件和空值入口，再实现；不改变原级联方式、分页或评分。
3. 固定同一来源版本对照两页原条件的经营响应及全部评分，核对多等级等于原各组合的并集且只计一次；检查、全量测试、构建、5173桌面和窄屏操作通过后更新业务交付及验证记录，再做一次独立代码复核。无自动提交、推送或生产发布。

## 要解决的问题

同一种操作在不同页有不同手感；商品与推广共用资料，却各自解释等级、生成选项和处理冲突条件。单页修复无法自动覆盖其他页。目标是让同一商品资料的含义一致、筛选操作一致，并保留各业务的真实范围。

## 具体实施

### 1. 共享资料分组，保持原资料和资格规则

在后端新增小型商品筛选投影模块（`product_board/filter_projection.py`），由M1/M2调用。现有`resolve_profile_fields`继续提供原始成员和资料状态；M1目录保留原`level`，新增以下两个筛选字段；M2沿用分组`level`和成员列表，查询共用同一规则：

| 输出            | 含义             | 规则                                                           |
| --------------- | ---------------- | -------------------------------------------------------------- |
| `level_group`   | 查询用等级组     | 一个非空等级保留原名；多个不同等级归“多等级”；无等级归“未匹配” |
| `level_details` | 原始不同等级列表 | 去重、稳定排序，不删除原等级、不取第一条或最后一条             |

M1经营总览、明细和M2商品目录及经营接口共同按`level_group`筛选。API适配层兼容原字段和旧链接；旧“×级/×级混合”链接保留原精确组合范围并回显对应条件，不静默扩大到全部多等级。用户重新选择“多等级”后才使用新分组范围；精确组合兼容保留到调用方迁完。M2已在本次修复中按此保护旧链接范围；M1本轮迁入相同规则并独立验收。原`level`、新品资格、清仓风险排除及SOP重点款判定不覆盖。先确定完整`listing_id`集合，再过滤事实；不把一条商品事实按多个等级展开后求和。

无需新增表或迁移，也无需重新同步上游。来源原值与资料关系已在现有表中；派生分组由统一规则生成，并纳入两域查询版本。

等级文字由`shared/products/levels.ts`共用，现有下拉组件继续使用；下面的其他公共交互仍是后续建议，本轮不实施。

### 2. 提取实际共用的前端能力

| 模块建议                           | 提供什么                                                             | 调用方保留什么                                                 |
| ---------------------------------- | -------------------------------------------------------------------- | -------------------------------------------------------------- |
| `shared/filters/SingleFilterField` | 从推广`FilterField`提取已验证的开合/失焦行为，组合而非覆盖调用方回调 | 标签、值、选项、禁用条件、查询行为；多选继续保持自己的选择行为 |
| `shared/filters/catalog`           | 校验唯一身份数与total、候选搜索、已选项名称回显                      | 页面目录加载器与查询键；不读取经营金额、不跨页混用候选         |
| `shared/filters/reconcile`         | 对轻量目录执行明确的联动策略，输出一次性状态补丁                     | 不直接发请求或写URL；页面一次更新自己的作用域                  |
| `shared/filters/query-state`       | 日期字符串校验、参数序列化、有限版本失效恢复等真正相同的能力         | 业务默认窗口、是否按报告选择、独立子区状态、成功/失败保旧展示  |

缓存键必须包含业务域、目录用途、日期、数据/规则版本和实际权限范围；M1总览/明细只有相同目录条件才复用。M1、M2、销售地区、售后报告不得共用一个全局选中状态。范围变化时旧候选可以暂用于回显，但不得作为新范围可选结果；新目录验证完整后再启用操作。

搜索草稿与已生效的经营关键词分别命名、分别处理。建议前后端统一裁首尾空格和大小写处理；内部空格保留。输入商品候选搜索不改变经营结果，选定商品才提交身份；既有经营关键词必须可见、可清除。规范化改变筛选含义的边界需用反例验证，不能只改显示文字。

### 3. 保留明确选择，避免隐式清理

推广页现按本次用户确认采用完整日期目录，候选不随其他条件变化；每次只更新操作字段，保留其他显式选择，无交集显示正常空结果。商品搜索只缩小候选，不参与经营范围清理。旧“新选择优先、清除冲突条件”的方案已取消，不再作为推广页目标。

M1、销售、售后和中心继续各自已确认行为。后续提取公共组件时，仅先共享开合、清除、搜索和完整性校验等实际共性；是否迁移筛选策略须逐页确认，不借重构改变业务范围、评分名单或日期窗口。

| ---- | ------------------------------------------ | ---------------------------------------------------------------------------------------- |

| 2    | M1/M2共享等级投影及完整目录契约            | 共有商品等级含义一致；多等级/未匹配可查；基础等级互斥；新品、评分、风险与SOP名单不变     |
| 3    | 提取单选/日期公共交互，逐页迁入            | 日期、店铺、品类、等级、运营重复点击/外部点击/键盘行为一致；多选不误收起；原请求范围不变 |
| 4    | 统一M1/M2联动，再整理共用目录工具          | 组合筛选、清空、旧URL、慢响应、空结果与快速切换全部一致；选项身份与经营对象逐组对账      |
| 5    | 销售/售后/中心接入适用的公共交互           | 各页自己范围及计算不变，不把ERP款式、平台链接或售后报告当成同一种商品身份                |

每步独立验证、独立提交，保留改前固定数据版本下的响应对照；共享模块变更检查所有调用页。回退代码须同时回退对应页面适配、契约及规则版本，不能只换前端标签。全程不回写来源、不改经营原值；无需数据迁移回退。新规则不得通过重新同步资料来掩盖代码版本失效。
