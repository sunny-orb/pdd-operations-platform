## API职责

查询版本同时纳入实际使用的共享商品资料共识、仓储、指标函数和六店策略文件。不能只因来源版本未变就继续接受旧目录版本；共享规则变化后，旧options/overview/days/diagnosis请求统一409，前端重取元信息及相容目录。该修复不写库、不改变经营计算；以模拟依赖修订的真实PG/API反例验证旧版拒绝、新版恢复及原数值不变。

/api/v1/promotion下meta/options/overview/days/diagnosis，mode=store|product。meta含各来源截至/成功/尝试/版本及推荐日期；其它请求显式data_version，409/422/503统一协议。overview合并趋势以同快照返回，days服务端分页。options普通查询保留有界候选；商品页使用catalog=true读取日期内完整去重资料目录，只有身份/名称/店铺/品类/等级/运营，不下发经营快照。目录按日期/发布版本缓存，前端仅做候选文字搜索，经营条件保留用户全部选择，金额/比率仍由API计算。完整listing_id区分跨店商品。店铺固定25行、商品25/50/100；商品模式不得依赖M1经营事实是否有同日行。名称恢复、展示投影及诊断分组查询见[data-contract 7.10](../data-contract.md#m2-v2-query-contract)。

业务答复以[data-contract 3.5.6](../data-contract.md#business-metric-questions)为准。meta及成交指标明确`payment_date/source_reported_payment_date`，两店铺来源分别保留日期角色；`attribution_window_days=NULL`，不填写未经来源证明的归因天数。规则版本为`sop-v1.4-m2-20261103-cost-availability`，查询定义指纹随实现更新；口径实施及隔离PG合成反例通过不等于真实来源完整性或点击级归因算法验收。

本次最小实施顺序：先在`test_promotion_api.py`补支付日边界/无点击输入仍保留源额、NULL及完整日门禁反例，在M3推广渠道测试核对同义状态；随后仅改推广`repository/query/diagnosis`元信息和说明、M1评分提示及M3推广提示/DTO，保持金额与评分算法不变；定向真实PG与前端测试确认后由主任务统一对账与重发相容评分。本段不授权上游查询、迁移或业务库重算。
