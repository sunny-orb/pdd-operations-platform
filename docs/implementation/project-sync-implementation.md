#### 每次检查与接收规则

- 检查取得的版本／修订与“最近成功接收”的版本比较，不能只与“上次检查”的值比较。变了但上次下载失败的来源，下一轮即使没有再次变化也必须重试；首次无已接收版本同样进入接收。
- 当前修订已成功接收且无新变化：只更新真实检查时刻和结果，跳过数据下载；对应派生结果若也已按相容输入成功生成则跳过重算。同日再次变化：重新接收该来源，随后仅重算受影响的结果；不再使用“今日完成便停查”的状态门禁。
- 来源接收与派生结果分别判断：评分／报告失败、缺失或输入版本落后时，在该业务已适用的时点独立重算，复用已成功接收的数据，不重拉来源；输入不相容则等待所需来源，来源检查成功不能冒充结果生成成功。保留范围的派生任务仍沿原时点，不因本轮策略扩大触发。
- 来源未到昨日、范围仍未接收完整或校验失败：保留实际日期与待更新／失败状态；后续时点再次判断／重试。明确目标日尚无新数据且可信修订未变时不反复下载旧版；缺少可靠修订证据不能按“没变”跳过必要对账。
- 元信息请求失败：展示检查失败并保留旧证据和可用数据，不推进接收标记，不以错误触发无限或无依据的全量读取。单源失败不阻断其他来源。
- 每次接收执行必要分页、业务键、范围和字段校验，稳定输入通过后原子发布，成功才推进接收版本；同步期间源再次变化则留待下一轮。任务success／网页时间／MAX(dt)不代表昨日全集完整，`complete_through`仍依来源证据。
- 调度接收显式时钟和逻辑槽，按来源保存失败及成功水位。实际接收仍使用各连接器既有的批准范围，不将范围缩成仅昨日；资料和目标按各自语义。当前入口用于当日执行，尚不提供任意历史业务窗口重放，未来接入外部调度可复用当日入口；历史回填需要另行显式传窗和验证。跨日重新检查，保留未成功接收的标记。

16:10与其余普通时点使用同一变化规则。获准范围的历史修订兜底按[每周对账方案](weekly-reconciliation.md)独立触发；普通检查和对账同轮共用来源接收。发现更新后接收失败，或接收成功但前后观测有变化，按检查点从最近失败或核对完成起等待至少 5 分钟，再由 Worker 复查该来源。每次失败重新计时，稳定接收后恢复正常周期。重试与到期时点合并，复用项目锁及完整发布校验。聚水潭和天气的正常监测周期沿用原配置，监测发现待重试的来源按 5 分钟间隔复查。页面刷新只读平台。

#### 旧调度收敛与迁移

本机CLI复用唯一既有触发器，配置开启新策略时按来源分配唯一生效策略：新范围退出这两条旧自动路径；保留范围仍以原频率／时点运行，所有入口继续共用既有互斥。不能直接全局关闭旧计划而影响聚水潭或天气，也不能让旧全项目任务继续包含已迁移的8张数仓表和2张飞书表。

同一逻辑时点重复触发必须去重；保留全量对账与普通变化接收的任务原因，但同源同范围已成功接收不得在同轮再下载。同一来源只有一份执行实例，崩溃租约恢复，错过多个时点只执行一次当前到期检查。手动补跑保留既有明确入口并共用锁／状态，不因页面刷新触发上游。商品三源已拆为可选来源接收和独立评分：已有基线时只读取选中表，复用未选中表的已发布版本；首次缺少基线时必须具备全部必要输入，不能隐式扩大指定来源下载。

计划模块只计算到期来源与原因；执行模块通过连接器接收／校验；仓储保存状态并负责事务；本机CLI或未来调度服务器只做触发适配。核心模块不依赖本机cwd、launchd或平台SDK，连接、运行日、逻辑时点、归档位置和凭据提供方式显式注入。[平台接管接口](sync-platform-handoff.md)已补来源粒度入口；不为未来迁移提前安装平台或引入Redis／消息队列。持久状态按下节专用数据库设计实施。

主要验收场景：同日成功后再更正；版本未再变但前次接收失败；元信息检查失败；昨日无记录；资料与目标无日经营日期；同表多用途；评分失败但来源成功；16:10对账与变更接收去重；新旧触发器同点／错点重复触发；聚水潭与天气保留范围；飞书只在两个固定时点；休眠、跨日积欠及重启恢复。本轮实际测试与运行限制见[固定时点验证](../validation/2026-11-04.md#source-fixed-schedule-20261104)；网页自动接入见[后续验证](../validation/2026-11-04.md#warehouse-auto-schedule-20261104)，不以单次已登录等同长期稳定运行。

### 实施步骤与状态设计

1. 核实只读表身份与网页时间。网页接口及账号登录协议保留历史证据；当前CLI按用户选择装配下节网页连接器。用户在项目专用窗口完成飞书登录，后台复用该专用会话，不导出个人浏览器身份、不把SQL账户当作网页身份；登录过期需重新登录。
2. 调度策略为纯函数（显式时刻、来源、配置）；仓储保存检查、接收及逻辑槽，执行器串行编排；CLI只装配。迁移来源退出旧整组及15分钟路径，保留6来源原路径。按源记录失败与成功，派生重算不推进来源标记。
3. 已有商品基线时各选中来源独立接收/发布，一源失败不阻断其他来源；首次缺输入时，仅全部必需输入可接收才原子建立基线，不扩大指定来源。复用其他已发布不可变版本；最终短事务再次锁定复用版本，原子发布关系。缺少复用输入时拒绝发布，不隐式扩大上游下载范围。
4. 真实PG验证同槽去重、重启、后续修订、失败重试、派生失败隔离、16:10对账和旧范围保留；核验API/页面、检查和构建。专用会话通过独立无界面读取、真实接收及回归后才切本机配置；此前保留旧计划，避免中断接收。

数据库设计：继续复用一个物理来源一行的 `source_checkpoints`（source_id主键，来源注册表唯一映射），不新增经营关系或缓存。Alembic12追加 `scheduled_slot_at`（带时区，最近已开始的固定槽）、`scheduled_attempts`（同槽0—2次，正常一次，崩溃20分钟后最多补一次）、`sync_started_at`、`sync_finished_at`、`sync_status`（running/succeeded/failed）；来源接收完成与上游检查完成分别存储，成功水位仍为accepted_fingerprint/accepted_at。字段均依赖source_id，无多值字段/事实复制；约束同步时间成对且完成不早于开始。网络读取不持DB事务；全局PG会话锁跨过程，写入使用短事务。崩溃后同槽仅在running且租约超时后受控恢复，后续槽继续；失败不推进水位。回退应用保留新增列，已有证据不删除；回退DDL仅允许无新状态的空列。字段字典与离线SQL随迁移维护。

### 网页自动读取接入（2026-11-04最新确认）

用户明确要求保留全部已定时点，自动进入数仓网页读取更新时间、变化后同步对应表，测试通过再启用；不是人工核对一次，也不要求开通数仓后台接口账号。聚水潭与天气不动，飞书仍按08:20/10:10。下列浏览器实现是技术选择，后续平台仍调用同一来源调度入口。

1. 新增独立网页连接器，通过项目专用浏览器读取8个固定表详情的可见物理表名和“数据更新时间”；核对页面URL/tableId、物理表名、时间格式，缺失/冲突/登录页都失败，不读取样例经营行，不调用SQL推定网页时间。每轮一个浏览器、一个页面串行复用，复查同表时强制重新加载，避免拿旧DOM。
2. 初次或过期由用户在专用浏览器完成飞书登录。只保存该浏览器中数仓域所需的登录状态到项目var私密目录（0600文件、0700目录、Git忽略），不扫描/复制个人Chrome状态，不保存密码、不输出Cookie。后台无界面加载此状态；失败不改旧成功数据，登录失效本轮只尝试一次并显示明确原因。进程退出释放浏览器与文件互斥。
3. 调度装配注入warehouse_reader，调度核心不依赖Playwright或本机路径。来源网页观察仍形成版本摘要，与accepted摘要比较；成功接收后重新读取网页确认稳定，再推进水位。本阶段仅调整观测适配器；后续周对账调整见[对账方案](weekly-reconciliation.md)。
4. 测试先覆盖真实网页结构样例的解析、身份错配/缺时间/多时间/非法日期、登录跳转、权限、会话复用/过期及浏览器退出；再以真实隔离PG验证同日更正、无变化不下载、失败下槽重试、同槽去重、两个旧路径均排除迁移来源。完成真实登录后，独立无界面进程读8表、与可见网页对照，再验证真实接收及下一次无变化跳过。
5. 验证通过后在项目互斥内原子启用source_schedule_enabled，保持唯一既有launchd入口；仅8张数仓和2张飞书退出旧全量/15分钟路径，4项聚水潭与2项天气及售后处理保留。核对状态API、页面计划文案和实际日志；需要用户完成网页登录时仅暂停依赖登录的部分，继续独立测试。回退仅关闭开关并保留状态证据，不删除数据或登录文件。

网页登录自然失效无法保证永久无人值守；应显示检查失败并重新登录后在下一固定槽重试，不能静默回退账号密码或拿旧网页时间当最新。源码中的账号/请求头连接器仅保留为未选用兼容入口，CLI当前选用网页读取，不新增第二套自动路径。

**调度与业务执行解耦。** 本机CLI与未来平台适配器调用同一`app.jobs.project_runtime.execute_project`，传入已有engine、稳定slot、显式运行路径及延迟取密函数；业务装配、来源接收/校验/发布、评分与报告由应用模块拥有。调度时槽/平台资源由触发器拥有，不向域模块传平台SDK；评分、运行、接收归档和配置/飞书工作根均显式定位。原互斥、租约、幂等及依赖规则不复制到新触发器。接口和整功能迁移/回退步骤见[sync-platform-handoff](sync-platform-handoff.md)，当前未接管平台。

当前手动更新使用同一CLI编排入口，返回任务/来源结果；状态弹窗仅提供只读刷新，自动检查负责发现变化后的接收。网页手动提交同步任务尚未实现。后续后台入口须立即返回任务ID/已有运行状态；选择来源、数据集和必要业务期间，指定期间补跑仍受原来源范围/权限和预算限制。若同逻辑范围已有任务在跑，登记/复用该任务或受控排队，不随点击量新增上游并发；手动任务与自动任务共用PostgreSQL互斥/租约和现有running唯一约束。普通看板刷新仅重读本地已发布结果，既不触发上游拉取，也不把接口等待变成长时间同步。用户只看当前真实进度、最后尝试/成功、实际截至/完整日和失败原因。

**增量及历史更正。** 有可靠修改时间/游标及稳定业务键才按增量读取，并使用交叠回看、分页同批/范围校验；dt通常是业务日，create_time通常是创建事件，均不自动充当修改水位。没有可靠增量时，按获准的完整范围快照/受控回看窗口重取并比对摘要；最近N天只能捕获窗口内修订，仍需周期更大范围对账与指定期间补跑，不能承诺旧退款或月结修订永远落在N天内。缺记录不代表删除；实际删除只依据明确删除事件/标记或已核完整枚举的范围快照，生成新版本并保留旧输入。当前项目编排对固定六店/批准日期范围执行两次完整分页且投影一致，再以受控reconcile_full_scope记录移除键/身份变更计数并发布新版本；既有行/版本不DELETE。普通未证明全范围的入口仍拒绝不明缺键；空商品/资料交付继续拒绝。读取枚举稳定不等于业务齐数，源软删除标签含义未证时只保留原值，不猜其业务效果。

**一次同步的边界。** 读取交付/固定批次→校验结构/键/单位/范围/完整性→在不可变候选版形成相容内容→短事务原子发布当前入口/可靠水位→按依赖重算资料关系、评分/报告→公布真实状态。上游有快照/批次令牌就固定它；分页读取中途上游变化且无法证明相容时不能把混批当完整成功，应有界重读或保留候选并说明缺口。源拉取不持有长时间发布事务/当前入口锁；数据无语义变化时复用已存内容版，但仍记录本次实际尝试与来源时间观测。新事实可先发布，依赖旧评分时明确待重算；未验依赖不拼成“全正常”。

首期单来源串行起步，跨源总并发仍按核实预算控制；执行互斥与失败接管复用[PostgreSQL锁机制](https://www.postgresql.org/docs/17/explicit-locking.html)及现有任务设计，发布/读取的一致性依据[事务隔离](https://www.postgresql.org/docs/17/transaction-iso.html)。调度到点不保证上游已有新数据，也不代表业务齐数。M3完成额随shop_daily新版本按已确认方案A重新汇总，已发布历史售后报告仍固定旧输入；更新历史报告须生成新报告修订。

“上游最多5并发”尚未确认，连接与查询、账号/资源组/全局、独享/共享、队列/拒绝及同步额度分别核实。连接池和任务遵守总预算，不随用户或API进程数放大。
