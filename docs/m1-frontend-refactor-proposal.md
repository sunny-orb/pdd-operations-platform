# 商品数据看板：前端重构方案

2026-10-22｜用户已确认头部保留热卖商品榜、接受第6节调整，授权实现前端与标注样例。本地功能分支实施中；不接数据库、不操作数仓、不调用AI、不发布。真实数据与模型验收单独进行。

## 1. 本次交付目标

先把 `/products` 做成结构规范、六块完整、交互可验证的前端。后续后端无论读取 PostgreSQL 还是经确认的其他来源，都通过同一 `/api/v1/products` 契约提供数据，页面组件不随来源重写。

| 保留线上原型                                                 | 本次整理内部结构                                                        | 尚未接入时                                                             |
| ------------------------------------------------------------ | ----------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 六块顺序、标题层级、卡片/图表/表格布局、评分展开、筛选和分页 | 分区组件、统一请求与类型、独立筛选状态、共享状态/格式组件、页面样式隔离 | 默认“尚未接入”；用明确标注的少量虚构开发样例验证交互，不搬线上经营快照 |

**原型依据：**[线上商品页](https://official-product-data-dashboard.gritty-koi-9822.chatgpt.site/?source=cockpit&focus=risk)，已核对公开发布代码及页面可访问文本，版本见[接口与数据设计](m1-api-and-postgresql.md)。本次截图通道返回空白，**未新增已验收的截图基线**；编码前需补采有效的固定视口基线，不凭空重设计配色。

现有 React + TypeScript + Vite、React Router、TanStack Query 沿用。不引入新的全局状态库，不迁入旧Next工程或全量快照。

评分卡数量较多时使用服务端分页；按组的总数/顺序由API给出，不下载全部评分后自行全局排序。不增加未确认的导出、投放预算调整、同步上游或告警写操作。

## 3. 筛选怎么联动

**保留三套独立状态，复用同一种筛选控件。**

| 筛选范围 | 影响区域                                         | 不受它影响的区域 |
| -------- | ------------------------------------------------ | ---------------- |
| 经营总览 | ①摘要、增长健康度、③汇总/链路/趋势、④诊断、⑤告警 | 新品评分、底表   |
| 新品评分 | ②新品列表、统计、档位详情                        | 经营总览、底表   |
| 商品明细 | ⑥底表和分页                                      | 上方五块         |

- 默认店铺/运营/品类/等级/商品均为全部；日期使用接口给出的推荐范围，不硬编码线上日期。日期信息未接入时不伪造“最新31日”。
- 总览和底表日期可以单日或区间；只填开始日表示单日。结束早于开始时提示并不请求，不静默颠倒输入。
- 上级筛选改变后只清除其下游已失效的选项；保留仍有效的选择。重置只作用当前范围，分页回第1页。
- 商品值使用店铺ID＋商品ID，名称仅展示；不能只用商品ID混合跨店记录。搜索在请求层防抖，分页和筛选交给后端。
- 近7/14/30日、热卖榜和评分各显示API返回的实际窗口；总览运营/品类/商品条件一致生效。固定观察新品的区块遇到等级冲突时显示范围说明/无适用结果，不暗中忽略筛选。
- 趋势指标、多指标/商品对比是展示状态；不改变总览口径。不同单位对比明确标“相对走势”，或分图显示，不共用误导的实际刻度。
- 摘要点击商品属于明确的跨区动作：更新总览商品范围并滚动定位；不悄悄覆盖评分/底表条件。`focus=risk`仅定位告警区，不触发处理/同步；`source`仅记录入口。

拟将三套条件用不同URL参数前缀保存，刷新/后退可恢复；输入先在本区状态更新，规范化后作为请求参数。URL中只放普通筛选，不放凭据或数据明细。

## 4. 代码如何组织

以下是拟建位置，本轮不创建目录或代码。按区块拆分，不把每一行文字拆成组件。

```text
apps/web/src/features/products/
  ProductsPage.tsx            页面组合、入口定位和整体数据版本
  api/
    contracts.ts             当前草案请求/响应类型；有业务OpenAPI后生成替换
    productsApi.ts           同源GET、参数序列化、响应校验和错误映射
    queries.ts               Query键、取消、刷新及版本协调
  state/
    filters.ts               三套筛选与URL转换，纯UI状态
  sections/
    brief/                   ①摘要、排行、建议、健康度
    scores/                  ②评分筛选、卡片、口径、弹窗
    overview/                ③总览筛选、汇总、链路、趋势
    DiagnosisCard.tsx        ④诊断
    alerts/                  ⑤告警表和说明
    days/                    ⑥明细筛选、表格、分页
  components/                商品选择、范围条等本页复用展示
  products.css               本页布局与样式，避免污染其他模块
  preview/                   仅开发预览的小样例/状态场景
```

公共层只提取已在本页重复使用的 `SectionState`、`FilterField`、`Pagination`、`MetricValue`、`StatusBadge`、对话框交互；HTTP继续复用并补强已有 `shared/api/client.ts`。涉及商品资料、评分、经营口径的内容留商品域，不提前建设通用低代码组件库。

`ProductsPage`只组合区块；区块接收查询结果/回调；渲染组件不自己fetch、不求和经营数据、不计算评分/风险、不直接调用AI。用户进一步要求优先组件库：统一Ant Design控件，统一Recharts图表，不自行绘制图表或引入多套UI库。

现有`App.tsx`的初始化大标题/连接面板不能继续占据商品页首屏：重构时把首页专属内容留首页，`/products`展示商品标题与来源状态；公共导航保留，系统检查保留轻量提示。其他路由内容不随之改版。

## 5. 接口与数据状态

### 请求与类型

- 使用[接口草案](m1-api-and-postgresql.md)的`filters/brief/scores/overview/trend/diagnosis/alerts/days`，本轮不新建后端业务接口。
- 首先取得可用范围和`data_version`，再并行查询各区块；Query键包含数据版本、范围名、规范筛选、指标/对比和分页。一次商品请求不要求推广全量下载成功。
- 新筛选取消旧请求，晚返回的数据不能覆盖当前条件。切筛选时不把旧条件结果当新结果显示；同条件刷新可保留旧结果并标“更新中”。
- 保留金额字符串和ID字符串，前端仅格式化；比例按0—1展示百分比。检查响应形状，非法/缺字段作为契约错误，不能转换成0。
- 业务未接入由接口能力/结构化状态说明。404表示路由未提供、网络错误表示请求失败，均不能擅自当“没有商品”或“数仓未接入”。
- meta按区块包含实际筛选/窗口、截至日、版本、完整性、缺数原因；显示业务状态，不把数据库表名/内部调试信息塞进运营流程。

### 状态分开定义，避免混用一个status

| 层次       | 建议字段 / 含义                                                                                             |
| ---------- | ----------------------------------------------------------------------------------------------------------- |
| 请求       | Query的pending/success/error；只说明HTTP请求状态                                                            |
| 区块可用性 | `availability`：ready/not_connected/not_supported/empty；请求成功也可能尚未接入                             |
| 数据覆盖   | `meta.completeness`：complete/partial/unknown；陈旧程度由截至日/来源更新说明判断，不由HTTP成功推定          |
| 计算/生成  | `computation_state`：not_started/pending/ready/failed；评分另有完整验证/待验证/未评分及原因，AI另有生成方式 |
| 人工闭环   | `workflow_state`及处理记录；未启用为null，不与评分/生成状态混为一谈                                         |

API未就绪返回结构化状态和空data，不用一组null指标伪装已完整接入。开发适配与未来真实响应使用同样结构。

### 每块独立处理的状态

| 状态              | 页面行为                                                                                                                                                                                            |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 尚未接入          | 区块标题/布局保留，正文“数据尚未接入”；数值为“—”，不填真实经营数字或空心假曲线                                                                                                                      |
| 首次加载          | 对应区块骨架；不设置虚构进度条，不整页遮挡其他已加载区块                                                                                                                                            |
| 正常              | 按API返回展示，带范围/截至日                                                                                                                                                                        |
| 无匹配结果        | “当前筛选下无商品/告警”，提供清除本区筛选；与未接入区分                                                                                                                                             |
| 真实零值          | 正常展示0；零销售不是缺数据，也不是加载失败                                                                                                                                                         |
| 部分缺数/不可计算 | 有依据的值照常显示，缺项为“—”并注明；缺去年数据不展示同比0%；评分显示待验证/缺项原因                                                                                                                |
| 数据较旧          | 保留同条件旧值并显示实际日期/提示；不自动换来源，不称实时最新                                                                                                                                       |
| 请求失败          | 仅该块错误与重试；同条件历史结果可保留，但标明“更新失败、当前为旧结果”                                                                                                                              |
| 评分/AI尚未生成   | 显示未计算/生成中/暂不可用；不影响基础指标和底表；评分旧输入要明确版本和日期                                                                                                                        |
| AI失败或规则降级  | 显示失败，或展示已由后台提供且明确标为“规则诊断”的结果；前端不自己编造替代结论                                                                                                                      |
| 来源版本改变      | 409后取消旧请求，统一撤下或遮罩锁定旧版本经营内容，再取得新版本并重新读取三套当前条件；同条件刷新保留旧值的规则不适用于切版。只协调重取一次，再冲突则停止循环并显示重试；不能新旧块同时作为当前结果 |

API尚未实现期间，默认未接入模式直接返回明确的前端接入状态，不假装网络GET成功。开发样例由请求层的开发适配提供同形响应，仅用少量虚构记录，持续展示“开发样例·非真实经营数据”；生产包不能自动启用或在请求失败时回退为样例。

AI生成属于后端任务，页面GET只读结果；若返回pending，可有界轮询（建议5秒、最多1分钟，隐藏页面暂停），到期提示稍后刷新，不触发重复AI任务。本阶段不调用模型，也不展示伪造的“AI已完成”。

## 8. 已确认的三点

1. **整体：**保持六块及线上顺序，先完成前端与数据状态，再接真实后端；三套筛选独立。
2. **头部第二榜：**保留线上“热卖商品（含新品）”，不替换成评分潜力榜。
3. **调整：**接受第6节的真实字段标签、规则/AI标识、未启用闭环状态和筛选一致性修正。

其余组件命名、请求层拆分及样式隔离由实现时按本方案处理；数据口径、评分规则和来源不因前端重构被默认为已确认。
