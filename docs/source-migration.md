## 架构与执行原则

在线链路保持为：前端 → FastAPI → 应用 PostgreSQL。独立任务读取当前指定上游，校验和发布后供查询；用户访问量不直接变成数仓查询量。

来源适配按实际需要实施：数仓连接器、必要的临时飞书连接器、受控文件导入各自转换为业务契约。页面和指标服务使用统一字段；源字段变化在连接器中处理，业务口径变化需单独确认和版本记录。

同一逻辑数据集、同一日期/店铺等业务范围，只允许一个来源成为发布依据。过渡期不同数据集可分别来自数仓和飞书；同一份数据不得因两边都存在而重复累计。默认整数据集切换，确需按日期分段时必须登记互斥边界，并验证历史修正的归属。

## 分阶段推进

1. **先确定交付清单。** 与辣椒确认已同步表、剩余需求的对应关系、分批时间及可交付范围。按看板所需数据组织，不以“搬完多少张表”作为唯一进度。
2. **先做一条可验证链路。** 优先选已有完整可用数据的最小业务范围；若与商品域不同，可以先用它验证真实同步，商品页继续按契约和样本开发。不要为等全部入仓暂停工程、API 和交互建设。
3. **未就绪数据分情况处理。** 在该模块联调前能交付的，先用样本；较长时间不能交付且业务必须使用的，再做最小飞书临时接入；低优先级模块可后移。时间表不明确时先明确承诺交付节点，不能默认为即将完成。
4. **逐数据集对账、发布和切换。** 候选数仓输入在隔离暂存区核验，通过后切换来源并发布完整有效版本，不让前端承担兼容逻辑。
5. **迁移后收口。** 该数据集稳定更新并完成约定观察期后停用临时任务；有其他用途的飞书表不由本项目删除。撤销不再需要的访问权限按公司流程执行。

样本和旧快照只能证明代码链路与交互，不能证明数据最新或正式接入。正式上线依赖真实来源、完整性和口径验收。商品评分等跨域功能还需商品、推广等依赖输入的粒度、范围和批次兼容，不能因一张表就绪就认定整个模块就绪。

## 切换验收

- 具备稳定的只读读取方式和约定查询预算；表存在不等于账号可读、数据完整或持续更新。
- 核验业务键、粒度、类型、单位、精度、空值、店铺/商品标识及历史覆盖。业务键不能沿用会随来源变化的内部记录 ID。
- 核验飞书公式、关联和汇总依赖：确认交付计算结果还是原始输入；若交付指标，仍需确定分母和跨范围聚合方法，不能直接平均比例。
- 在相同业务日期、范围和数据截止点下对账记录数、唯一键、金额及关键指标，包含历史、同比、退款修正等场景。差异逐项解释，容忍标准由业务确认，不能静默忽略。
- 实测后续更新、迟到数据、历史回补、重复、删除和失败恢复；不仅比较一次静态样本。
- 确定切换后的历史数据如何替换或保留，避免新旧来源记录并存、历史口径割裂或后续增量漏掉旧记录。
- 发布来源版本及对应批次后再推进水位；保留上一有效版本或经过验证的恢复路径。只有已经实现并验证恢复，才能声称支持回退。
- 数仓失败时保留上一有效版本并显示延迟/失败状态。需回退飞书时，先核验权限、覆盖与口径，再通过明确切换任务执行，禁止自动混源。
