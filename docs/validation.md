## 旧系统基线与可复跑材料

旧系统的测量与来源核查、当前新系统本机检查分别记账。先选影响日常判断的核心页面和高频争议指标，补齐以下三类材料，再逐步扩展；某页缺基线要写清限制，不能把已有新系统计时当作旧系统对照。

| 基线 | 固定哪些条件                                                                                        | 留下什么结果                                                                                           |
| ---- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 性能 | 页面/版本、设备、浏览器、视口/缩放、网络、数据范围/数量、冷热缓存、负载和有效样本数；明确计时起止。 | 从导航到核心指标可用、首屏绘制、查询P95、筛选耗时、错误率/内存；并发和超时场景下的表现及原始测量记录。 |
| 数据 | 核心指标、公式版本、店铺/商品/日期、单位/分母、资料视角、权限、输入来源/版本与覆盖。                | 可执行的核对步骤、预期值与实际值、差异及容差依据、刷新规律、延迟、上游依赖和口径歧义。                 |
| 使用 | 统计期间、获准日志或访谈方法、真实角色及数据可见范围。                                              | 各页访问频次、常用筛选与下钻路径、导出/汇报等真实用途；没有证据的“无人使用”判断不得登记为事实。        |

旧系统没有查询API时，分别测静态资源下载、解压和浏览器计算，不虚构旧API响应时间；新接口和数据库耗时单列，不能与完整首屏混算。P95须保留样本、计算方法和失败请求情况，小样本开发计时只记观察值。

每份基线包记录代码及资源版本、环境、输入标识、可重复执行的命令/步骤、预期与实际结果、报告/截图位置、日期和执行/确认人。记录版本号不代表保存了当时数据：输入会被覆盖时，先确定获准的样例、来源版本或备份能否重建；不能复现原数值的地方明确标注。

无敏感数据的测试代码、合成样例和执行说明可随代码维护；真实经营输入、日志和截图放获准的私有验收目录，记录引用及校验值，禁止把整套旧快照搬进仓库或新查询主链路。尚未编写的复测脚本、尚未采集的日志均保持待办，本文不表示基线包已存在。

至少做一次旧系统异常数字回溯：给定卡片、对象和期间，依次找到请求条件、规则、输入版本和源表字段。记录异常原因、证据及处理归属；无法取得的加工环节标为断链，不擅自进入ETL。追溯与差异解释按[data-contract第10节](data-contract.md#migration-contracts)。

<a id="delivery-gates"></a>

## 交付和上线前怎样判断通过

这些条件检查的是对应范围，不要求全项目等到同一阶段再继续。已有M1技术交付保留原日期与范围；新增规则不补签历史验收。未决项只限制依赖它的结果，独立已授权工作可以并行。不涉及的检查写明“不适用”及理由，不为凑齐清单增加功能；缺旧基线不阻止已授权的调查和设计，但不能据此宣称优化已经达标。

| 检查点                      | 通过前必须有的材料                                                                                                                               |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Gate 1 基线评审             | 核心旧页面的测量在约定环境可复测；指标当前理解由业务确认；使用情况有来源或明确缺口；完成一次异常数字回溯，断链已标注。                           |
| Gate 2 设计与兼容           | 本次数据/接口/URL及权限保留清单有真实消费方确认；物理设计满足相关前置项；新旧对账方案及回切操作单完成推演或演练。尚无消费方证据不等于无需兼容。  |
| Gate 3 每个交付功能         | 数据→接口→页面的完整路径可验；同条件数据核对、约定环境下布局/交互、正常及拒绝访问路径、基本键盘操作有结果，未通过项不发布。                      |
| Gate 4 指标与来源           | 核心指标确认记录齐全，已有争议有处理决定；能演示卡片到源表的路径或准确说明断链；差异报告按事先确认的容差检查。断链若影响正确性，不发布依赖结果。 |
| Gate 5 扩大到全部目标用户前 | 下表四层验收均有本次范围的结果，至少一位真实角色走通业务场景；未通过项已处理或有明确批准的限制，数字及权限错误不能豁免。                         |
| Gate 6 切换与退役           | 观察记录符合已批准阈值和时长，异常处理与回切耗时有证据；最终数据核对、活跃依赖和消费方确认完成，符合architecture的退役条件。                     |

<a id="layered-acceptance"></a>

### 四层验收分别留下什么

| 验收层     | 要检查什么                                                                                                   | 验收材料                                  |
| ---------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------- |
| 数据       | 同输入、窗口和权限下与权威来源核对；公式及页面一致，覆盖零值、缺数、边界日期和关联；已知旧错误不作正确答案。 | 数据比对报告、口径确认记录及差异处理。    |
| 视觉与操作 | 按已选浏览器×视口检查截图、布局、弹层、图表和键盘操作；保留已确认的原型差异。                                | 同条件截图、交互结果、差异及确认记录。    |
| 性能与运行 | 正式或预发环境按基线负载比较首屏、查询P95和错误率；检查上游超时、查询失败、同步中断及恢复。                  | 性能对比、失败/降级与恢复演练、实际耗时。 |
| 业务判断   | 真实使用者完成[页面场景](requirements.md#business-acceptance)，找到问题、依据和下一步核查事项。              | 角色与步骤、实际判断、反馈及未解决问题。  |

静态布局用固定状态截图比较；动态数字和异步图表用固定输入、语义或数值断言核对，必要像素容差写明依据。不能为了通过截图把关键数字遮掉；更新基线要保留原因和认可差异。截图纳入受控验收资料，含经营信息时不直接提交Git。

权限先按已确认的“获准用户可看全部店铺”验证，覆盖未登录拒绝、越权操作及来源账号隔离；将来若批准分店铺/行列权限，再补权限过滤后的聚合测试。管理员本机可连库不替代应用权限验收。

降级必须让使用者看懂：同条件旧成功值可带日期和失败状态保留，缺项单独说明；禁止改读未批准来源、回退经营样例或把失败当零。没有引入缓存的功能不为满足清单临时增加缓存。恢复既验证入口切回，也在隔离实例验证备份恢复后的金额、版本和可用范围。

每次记录本次范围/版本、执行及确认人、环境与可复跑步骤、输入能否重建、预期/实得及容差或耗时、未通过项及处理决定，并链接相应材料。只写“检查通过”不算完整验收；实际状态仍只在TODO维护。
